# 小满商城生产部署：服务器与域名

**WHAT THIS DOCUMENT IS**

A runbook for putting XiaoMan Mall on a single Linux server with a real domain:
DNS, firewall, Node.js, systemd, Nginx, TLS certificates, verification, logs,
backup, rollback, and the common 502/504/SSE/Cookie failures. It also covers the
optional Docker Compose path. The app is dependency-free Node.js; there is no
build step and no npm install in production.

**这篇文档是干什么的**

把“一台服务器 + 一个正式域名”从零部署到可访问的完整操作手册：准备服务器、
解析域名、放行端口、安装 Node、拉代码、准备数据目录、配置 systemd 和 Nginx、
申请 HTTPS 证书、验收、看日志、备份、回滚，以及排查 502/504/SSE 不流式/
Cookie 不生效等常见问题。最后附可选的 Docker 方案。

> 文中域名统一用 **mall.example.com** 占位，服务器 IP 用 **203.0.113.10**
> 占位，邮箱用 **admin@example.com** 占位。复制命令前先替换成自己的真实值。
> 不要把真实域名、IP、密钥写进仓库里的示例文件。

> 本文的验证环境是开发机（Windows + Node v24.21.0 + 临时数据目录），
> 不是正式服务器。文中标注“本地实测”的数字只用于说明预期行为；
> 上线时请按第 13 节的验收清单在服务器上重新测一遍。

## 0. 先看整体架构

~~~text
浏览器
  │  https://mall.example.com:443
  ▼
Nginx（TLS 终止、gzip、安全响应头、SSE 不缓冲）
  │  http://127.0.0.1:3000
  ▼
Node.js  server/index-服务入口.js
  │
  ├─ /api/*        业务接口（商品、购物车、订单、认证、AI 助手）
  └─ 其它路径      public/ 下的 HTML、CSS、JS、SVG
  │
  ▼
/var/lib/xiaoman-mall/*.json   商品、分类、购物车、订单、用户、会话
/var/lib/xiaoman-mall/agent-traces.jsonl   AI 助手调用轨迹（可选）
~~~

要点：

- 后端只监听 **127.0.0.1:3000**，公网只能通过 Nginx 的 443 进来。
- 3000 端口不要对公网开放；云安全组和系统防火墙都要挡。
- 数据是 JSON 文件，没有数据库；备份和回滚的核心就是这些文件。
- 没有 npm 依赖，**不需要 npm install**；拉代码后直接 node 启动。
- 现在应用层已经有 **GET /api/health** 和基础安全响应头；HTTPS、HSTS、CSP
  等由 Nginx 层补。两层都发同名头会造成重复，Nginx 配置里已用
  **proxy_hide_header** 处理，验收时检查同名头只出现一次。

## 1. 前置条件与境内/境外差异

### 1.1 服务器

| 项目 | 最低 | 建议 |
| --- | --- | --- |
| 系统 | Ubuntu 22.04 / 24.04 LTS x86_64 | 同上，保持安全更新 |
| CPU | 1 核 | 2 核 |
| 内存 | 1 GB（需要 swap） | 2 GB 及以上 |
| 磁盘 | 10 GB | 20 GB 以上，日志/备份另算 |
| 权限 | sudo 或 root | 日常用普通用户 + sudo |
| 网络 | 公网 IPv4，80/443 可入 | 需要 IPv6 再加 AAAA |

Debian 12 也可用，把 apt 命令原样执行即可。CentOS/RHEL 的 firewalld、
SELinux 和 NodeSource 命令不同，本文不展开；如果用 RHEL 系，至少确认
SELinux 没有拦住 Nginx 反代（**setsebool -P httpd_can_network_connect 1**）。

### 1.2 域名

- 一个可以改 DNS 的正式域名，例如 **mall.example.com**。
- 能添加 A 记录（IPv4）；有 IPv6 再加 AAAA。
- 能等待 DNS 生效（通常几分钟，最长 24–48 小时）。
- 证书申请要求 80 端口能从公网访问；如果域名前面套了 CDN，先关代理
  或确认 CDN 放行 **/.well-known/acme-challenge/**。

### 1.3 境内服务器：必须 ICP 备案

服务器在中国大陆境内时：

- 域名必须完成 **ICP 备案**（通过云厂商备案系统提交），备案通过前
  云厂商通常会拦截 80/443，网站不能对公网提供访问。
- 备案周期常见 1–3 周，受管局审核影响；上线排期要预留。
- 备案后通常还要做 **公安联网备案**（各地要求不同，按云厂商提示）。
- 备案主体、域名实名信息、网站内容要一致；个人备案不能做经营性内容。
- 不要用“先上线再备案”绕过：会被拦截或关停，也可能影响域名。

### 1.4 境外服务器：不需要 ICP 备案

服务器在香港、澳门、台湾或境外（新加坡、日本、美国等）时：

- 不需要中国大陆的 ICP 备案，域名解析后可直接部署。
- 仍要遵守服务器所在地法律、云厂商条款和域名注册商规则。
- 面向中国大陆用户时延迟可能更高；可考虑香港/新加坡等近端区域。
- 如果之后把服务器迁回大陆，或使用大陆 CDN/加速产品，通常仍要备案；
  以云厂商和管局要求为准。

> 选“境内还是境外”是部署前第一个决定：境内先备案，境外先确认延迟和
> 数据合规。不要等代码都部署完了才发现 80/443 被备案拦截。

## 2. DNS：把域名指到服务器

在域名解析控制台添加：

| 主机记录 | 类型 | 值 | TTL |
| --- | --- | --- | --- |
| mall | A | 203.0.113.10 | 300（首次） |
| www | CNAME | mall.example.com | 300（可选） |
| mall | AAAA | 服务器的 IPv6（可选） | 300 |

说明：

- 首次切换用 300 秒 TTL，方便回退；稳定后可改 3600。
- 只添加 AAAA 的前提是服务器真的有可用 IPv6，并且防火墙放行了 443；
  否则部分用户会优先走 IPv6 然后超时。
- **www** 要不要加看你需要；如果加，Nginx 的 **server_name** 也要加，
  或者单独做一个 301 到主域名。
- 如果使用 Cloudflare 等 CDN：首次签发证书时建议先设为“仅 DNS”（灰云），
  证书拿到后再决定是否开代理；开代理时 SSL 模式选 **Full (strict)**，
  并确认 CDN 不缓冲 SSE、不覆盖 **X-Accel-Buffering**。

验证：

~~~bash
dig +short mall.example.com A
dig +short mall.example.com AAAA
# 没有 dig 时：
getent hosts mall.example.com
nslookup mall.example.com
~~~

期望输出里有你的服务器 IP。DNS 没生效前不要急着申请证书。

## 3. 防火墙与云安全组

### 3.1 云厂商安全组

入方向只放行：

| 端口 | 来源 | 用途 |
| --- | --- | --- |
| 22/tcp | 你的固定 IP（尽量） | SSH 管理 |
| 80/tcp | 0.0.0.0/0, ::/0 | HTTP 跳转 + ACME 验证 |
| 443/tcp | 0.0.0.0/0, ::/0 | HTTPS |

不要放行 3000、3306、6379 等内部端口。需要从本机调试时用 SSH 隧道：

~~~bash
ssh -L 3000:127.0.0.1:3000 user@203.0.113.10
# 然后本机浏览器访问 http://127.0.0.1:3000/
~~~

### 3.2 系统防火墙（Ubuntu ufw）

~~~bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 22/tcp
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status verbose
~~~

确认 80/443 是 ALLOW，3000 没有出现在列表里。云安全组和 ufw 是两层，
两层都要放行 80/443，缺一层就会超时。

### 3.3 检查监听地址

部署完成后：

~~~bash
sudo ss -lntp | grep -E ':80|:443|:3000'
~~~

期望：

- 80/443 由 **nginx** 监听，地址是 **0.0.0.0** 和/或 **[::]**。
- 3000 由 **node** 监听，地址必须是 **127.0.0.1:3000**，不能是
  **0.0.0.0:3000**（除非你明确要直连并已用防火墙挡住）。

## 4. 安装 Node.js 24

项目 **package.json** 要求 **node >= 18**；生产按任务要求装 Node 24。
推荐 NodeSource 的 apt 源，systemd 能直接拿到 **/usr/bin/node**。

~~~bash
sudo apt-get update
sudo apt-get install -y curl ca-certificates git
curl -fsSL https://deb.nodesource.com/setup_24.x -o /tmp/nodesource_setup.sh
sudo bash /tmp/nodesource_setup.sh
sudo apt-get install -y nodejs
node -v
command -v node
~~~

期望：

- **node -v** 输出 **v24.x.x**。
- **command -v node** 输出 **/usr/bin/node**（NodeSource 的默认路径）。

如果输出不是 /usr/bin/node（例如 nvm 装在用户目录），有两个选择：

1. 改用 NodeSource 重装，保证 systemd 能用 /usr/bin/node；
2. 保留现有 Node，但把 **deploy/xiaoman-mall.service** 里的
   **ExecStart** 改成 **command -v node** 的绝对路径。

不要把 nvm 的初始化脚本写进 systemd；systemd 不读用户的 .bashrc。

可选：1 GB 内存的机器加 2 GB swap，避免构建/日志高峰被 OOM 杀掉。

~~~bash
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
free -h
~~~

## 5. 创建运行用户和目录

不要让 Node 以 root 运行。创建一个不能登录的系统用户：

~~~bash
# 已存在就跳过
getent passwd xiaoman || sudo useradd --system --user-group \
  --home-dir /opt/xiaoman-mall \
  --shell /usr/sbin/nologin \
  xiaoman

sudo install -d -m 750 -o xiaoman -g xiaoman /opt/xiaoman-mall
sudo install -d -m 750 -o xiaoman -g xiaoman /var/lib/xiaoman-mall
id xiaoman
~~~

目录约定：

| 路径 | 用途 | 属主/权限 |
| --- | --- | --- |
| /opt/xiaoman-mall/xiaoman-mall | 代码 | xiaoman:xiaoman，750 |
| /var/lib/xiaoman-mall | 数据 JSON | xiaoman:xiaoman，750 |
| /etc/xiaoman-mall.env | 环境变量/密钥 | root:root，600 |
| /etc/systemd/system/xiaoman-mall.service | systemd 单元 | root:root，644 |
| /etc/nginx/sites-available/xiaoman-mall.conf | Nginx 站点 | root:root，644 |

**/var/lib/xiaoman-mall** 也会由 systemd 的 **StateDirectory=xiaoman-mall**
在启动时创建/校正属主；这里先手工建，是为了在第一次启动前就能放商品 JSON。

## 6. 拉代码

### 6.1 第一次部署

~~~bash
sudo -u xiaoman git clone git@example.com:your-org/xiaoman-mall.git \
  /opt/xiaoman-mall/xiaoman-mall
cd /opt/xiaoman-mall/xiaoman-mall
git log -1 --oneline
ls -l server/index-服务入口.js package.json
~~~

把 **git@example.com:your-org/xiaoman-mall.git** 换成你的真实仓库地址。
私有仓库用部署密钥（deploy key），不要把个人 SSH 私钥放到服务器。
没有 Git 仓库时，也可以用 **rsync** 从本地上传，但要在服务器上保留一份
可回滚的版本（见第 16 节）。

### 6.2 更新已有部署

~~~bash
cd /opt/xiaoman-mall/xiaoman-mall
sudo -u xiaoman git fetch --all --tags
sudo -u xiaoman git log --oneline -5
sudo -u xiaoman git checkout <tag-or-commit>
sudo systemctl restart xiaoman-mall
curl -fsS http://127.0.0.1:3000/api/health
~~~

更新前先备份数据（第 15 节）。不要用 **git reset --hard** 覆盖服务器上
未提交的配置；配置应该放在 **/etc**，不要放在代码目录里。

### 6.3 不需要 npm install

项目零第三方依赖，**package.json** 没有 dependencies。不要在生产机跑
**npm install**，也不要提交 **node_modules**。启动只需要：

~~~bash
node server/index-服务入口.js
~~~

## 7. 准备数据目录（商品/分类必须先复制）

应用启动时 **XM_DATA_DIR** 指向的目录不存在会自动创建，但**商品和分类
不会自动生成**。首次部署必须把仓库里的两个种子文件复制过去：

~~~bash
sudo -u xiaoman cp \
  /opt/xiaoman-mall/xiaoman-mall/server/data/products-商品数据.json \
  /var/lib/xiaoman-mall/
sudo -u xiaoman cp \
  /opt/xiaoman-mall/xiaoman-mall/server/data/categories-商品分类.json \
  /var/lib/xiaoman-mall/
sudo chown xiaoman:xiaoman /var/lib/xiaoman-mall/*.json
sudo chmod 640 /var/lib/xiaoman-mall/*.json
ls -l /var/lib/xiaoman-mall/
~~~

当前仓库里这两个文件的规模（本地实测）：

- **products-商品数据.json**：26 条商品。
- **categories-商品分类.json**：6 个分类。

验证条数：

~~~bash
node -e "const fs=require('fs');const p=JSON.parse(fs.readFileSync('/var/lib/xiaoman-mall/products-商品数据.json','utf8'));const c=JSON.parse(fs.readFileSync('/var/lib/xiaoman-mall/categories-商品分类.json','utf8'));console.log('products='+p.length,'categories='+c.length)"
~~~

运行时还会生成/使用这些文件，**不要删**：

| 文件 | 内容 |
| --- | --- |
| carts-购物车数据.json | 购物车 |
| orders-订单数据.json | 订单 |
| users-用户数据.json | 用户 |
| sessions-用户会话.json | 登录会话 |
| conversations-助手会话.json | AI 对话历史（首次使用时生成） |
| agent-traces.jsonl | AI 调用轨迹（可选，JSONL） |

注意：

- **XM_DATA_DIR** 在 Node 进程 require 时读取；改了环境变量必须重启服务。
- 更新商品/分类时，先备份旧文件；不要用新种子覆盖掉运行中的订单/用户。
- 数据文件是同步 JSON 写入，单进程、单机够用；不要多个实例同时写同一个
  数据目录，否则会互相覆盖。

## 8. 环境变量与密钥

### 8.1 安装模板

~~~bash
cd /opt/xiaoman-mall/xiaoman-mall
sudo install -m 600 -o root -g root \
  deploy/xiaoman-mall.env.example /etc/xiaoman-mall.env
sudoedit /etc/xiaoman-mall.env
sudo chmod 600 /etc/xiaoman-mall.env
sudo chown root:root /etc/xiaoman-mall.env
sudo ls -l /etc/xiaoman-mall.env
~~~

### 8.2 变量说明

| 变量 | 示例 | 说明 |
| --- | --- | --- |
| PORT | 3000 | 后端端口；改这里要同步改 Nginx upstream |
| HOST | 127.0.0.1 | 只监听本机；Docker 里用 0.0.0.0 |
| XM_DATA_DIR | /var/lib/xiaoman-mall | 数据目录 |
| XM_TRACE_FILE | /var/lib/xiaoman-mall/agent-traces.jsonl | AI 轨迹文件，可选 |
| AGENT_MODE | local | local=本地规则，不需要 Key；llm=调用大模型 |
| AGENT_API_KEY | 空 | 大模型密钥；只放服务器，不提交 |
| AGENT_BASE_URL | https://api.deepseek.com/v1 | OpenAI 兼容接口地址 |
| AGENT_MODEL | deepseek-chat | 模型名 |
| AGENT_TIMEOUT_MS | 30000 | 单次大模型超时，毫秒 |

首次上线建议 **AGENT_MODE=local**，不需要 API Key，先把链路跑通：

~~~bash
sudo sed -i 's/^AGENT_MODE=.*/AGENT_MODE=local/' /etc/xiaoman-mall.env
sudo systemctl restart xiaoman-mall
curl -fsS http://127.0.0.1:3000/api/health
~~~

确认 **mode** 是 **local**。切到大模型：

~~~bash
sudoedit /etc/xiaoman-mall.env
# 改成：
# AGENT_MODE=llm
# AGENT_API_KEY=你的真实密钥
sudo systemctl restart xiaoman-mall
curl -fsS http://127.0.0.1:3000/api/health
~~~

**mode** 变成 **llm** 后，再用一条真实消息测 **/api/agent/chat**。如果 Key
无效，助手会报错或退回本地规则；不要只看进程是否启动。

### 8.3 密钥规则

- **AGENT_API_KEY 只放服务器**的 **/etc/xiaoman-mall.env**，不要写进
  **deploy/xiaoman-mall.env.example**、Compose 文件、Git、工单、截图。
- 文件权限必须是 **root:root 600**；systemd 以 root 读文件后再降权运行，
  应用进程本身不需要读这个文件。
- 不要用 **systemctl show -p Environment** 排查：它会把 **AGENT_API_KEY**
  明文打印出来。用 **/api/health** 的 **mode** 字段确认模式即可。
- 怀疑泄露时：先在模型供应商后台吊销/轮换 Key，再改服务器文件并重启。
- 备份 **/etc/xiaoman-mall.env** 时要加密；不要把它和普通代码备份放一起。
- 值里如果有空格或 **#**，用双引号包起来；不要写 **export**，systemd 的
  EnvironmentFile 不是 shell 脚本。

## 9. systemd：让服务常驻

### 9.1 安装单元

~~~bash
cd /opt/xiaoman-mall/xiaoman-mall
sudo cp deploy/xiaoman-mall.service /etc/systemd/system/xiaoman-mall.service
sudo systemctl daemon-reload
sudo systemctl enable --now xiaoman-mall
systemctl status xiaoman-mall --no-pager
~~~

期望 **Active: active (running)**，并且 **Main PID** 对应的命令是
**/usr/bin/node server/index-服务入口.js**。

### 9.2 本地验收

~~~bash
curl -fsS http://127.0.0.1:3000/api/health
curl -fsS 'http://127.0.0.1:3000/api/products?pageSize=60' | head -c 300
ss -lntp | grep 3000
~~~

健康检查返回的 **data** 里应有：

- **status: ok**
- **version: 1.0.0**（跟 package.json 一致）
- **mode: local** 或 **llm**
- **uptimeSeconds**、**now**

### 9.3 单元里的关键项

- **User=xiaoman / Group=xiaoman**：非 root 运行。
- **WorkingDirectory=/opt/xiaoman-mall/xiaoman-mall**：代码目录。
- **EnvironmentFile=/etc/xiaoman-mall.env**：环境变量/密钥。
- **ExecStart=/usr/bin/node server/index-服务入口.js**：绝对路径。
- **Restart=always / RestartSec=3**：崩溃自动拉起；60 秒内超过 5 次会停，
  避免无限重启刷日志（**StartLimitIntervalSec/StartLimitBurst**）。
- **StateDirectory=xiaoman-mall**：自动创建 **/var/lib/xiaoman-mall** 并
  chown 给 xiaoman；配合 **StateDirectoryMode=0750**。
- **ProtectSystem=strict**：整个文件系统只读，只有 **ReadWritePaths** 和
  **StateDirectory** 允许写；应用只能写数据目录和 /tmp。
- **NoNewPrivileges=true、CapabilityBoundingSet=、PrivateTmp、
  PrivateDevices、ProtectHome、ProtectKernelTunables/Modules/Logs、
  RestrictAddressFamilies**：收紧权限。
- **MemoryDenyWriteExecute** 故意注释：V8 需要 JIT 写可执行内存，打开会让
  Node 起不来。

### 9.4 服务起不来时

~~~bash
systemctl status xiaoman-mall --no-pager -l
journalctl -u xiaoman-mall -n 100 --no-pager
systemd-analyze verify /etc/systemd/system/xiaoman-mall.service
~~~

常见原因：

- **/etc/xiaoman-mall.env** 不存在或权限不对：systemd 直接失败。
- **ExecStart** 的 node 路径不对：把 **command -v node** 的结果填进去。
- **WorkingDirectory** 不存在：代码没拉到约定路径。
- **226/NAMESPACE** 或 permission denied：先注释 **SystemCallFilter** 两行
  和 **RestrictNamespaces** 定位，再逐项加回；不要整套删掉。
- 端口被占用：见第 18 节 **EADDRINUSE**。

改完单元文件要 **sudo systemctl daemon-reload**；只改环境变量则
**restart** 即可。

## 10. Nginx + HTTPS：先引导证书，再上正式配置

正式配置引用了 **/etc/letsencrypt/live/mall.example.com/** 下的证书；
证书不存在时 **nginx -t** 会失败。所以第一次要先用一个**只开 80 的临时
站点**把证书签下来，再换正式配置。

### 10.1 安装 Nginx 和 certbot

~~~bash
sudo apt-get update
sudo apt-get install -y nginx certbot
nginx -v
certbot --version
sudo systemctl enable --now nginx
~~~

### 10.2 准备 ACME 目录，停掉默认站点

~~~bash
sudo mkdir -p /var/www/certbot
sudo chown -R www-data:www-data /var/www/certbot
sudo rm -f /etc/nginx/sites-enabled/default
~~~

### 10.3 临时 HTTP 站点（只用于签证书）

~~~bash
sudo tee /etc/nginx/sites-available/xiaoman-mall-bootstrap.conf >/dev/null <<'EOF'
server {
    listen 80;
    listen [::]:80;
    server_name mall.example.com;

    location ^~ /.well-known/acme-challenge/ {
        root /var/www/certbot;
        default_type "text/plain";
        try_files $uri =404;
    }

    location / {
        return 200 "bootstrap";
    }
}
EOF
sudo ln -sf /etc/nginx/sites-available/xiaoman-mall-bootstrap.conf \
  /etc/nginx/sites-enabled/xiaoman-mall-bootstrap.conf
sudo nginx -t
sudo systemctl reload nginx
curl -i http://mall.example.com/.well-known/acme-challenge/ping
~~~

最后一条期望 **404**（文件不存在是正常的），说明 80 端口和路径已经通了。
如果返回超时/连接拒绝，先查 DNS、云安全组、ufw，不要继续申请证书。

### 10.4 申请证书（webroot）

~~~bash
sudo certbot certonly \
  --webroot -w /var/www/certbot \
  -d mall.example.com \
  --email admin@example.com \
  --agree-tos --no-eff-email --non-interactive
sudo certbot certificates
~~~

期望看到 **Certificate Name: mall.example.com**，以及：

~~~text
/etc/letsencrypt/live/mall.example.com/fullchain.pem
/etc/letsencrypt/live/mall.example.com/privkey.pem
~~~

如果失败：

- **DNS problem**：A 记录没生效，或解析到了旧 IP。
- **Timeout / connection refused**：80 没放行，或 CDN 代理没放行 ACME。
- **too many failed authorizations / rate limit**：先用 **--staging** 调试，
  成功后再去掉 staging；不要反复打生产接口。
- **unauthorized**：webroot 路径和 Nginx 的 **root** 不一致。

调试用 staging（证书不被浏览器信任，只验证流程）：

~~~bash
sudo certbot certonly --staging \
  --webroot -w /var/www/certbot \
  -d mall.example.com \
  --email admin@example.com \
  --agree-tos --no-eff-email --non-interactive
~~~

调试完用 **sudo certbot delete --cert-name mall.example.com** 删掉 staging
证书，再按上面的生产命令重新签。

### 10.5 切到正式配置

~~~bash
cd /opt/xiaoman-mall/xiaoman-mall
sudo rm -f /etc/nginx/sites-enabled/xiaoman-mall-bootstrap.conf
sudo cp deploy/nginx-小满商城.conf \
  /etc/nginx/sites-available/xiaoman-mall.conf
# 把占位域名换成真实域名；证书路径也会一起换
sudo sed -i 's/mall\.example\.com/你的真实域名/g' \
  /etc/nginx/sites-available/xiaoman-mall.conf
sudo ln -sf /etc/nginx/sites-available/xiaoman-mall.conf \
  /etc/nginx/sites-enabled/xiaoman-mall.conf
sudo nginx -t
sudo systemctl reload nginx
~~~

**nginx -t** 必须通过再 reload。若报证书文件不存在，检查 **certbot
certificates** 的证书名和配置里的路径是否一致；certbot 的目录名是域名，
不是任意名字。

### 10.6 证书自动续期

certbot 的 apt 包通常自带 systemd timer：

~~~bash
systemctl list-timers | grep -i certbot
sudo certbot renew --dry-run
~~~

续期成功后要让 Nginx 重新加载证书，加一个 deploy hook：

~~~bash
sudo install -d -m 755 /etc/letsencrypt/renewal-hooks/deploy
sudo tee /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh >/dev/null <<'EOF'
#!/bin/sh
systemctl reload nginx
EOF
sudo chmod 755 /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh
sudo certbot renew --dry-run
~~~

检查到期时间：

~~~bash
sudo certbot certificates
echo | openssl s_client -servername mall.example.com \
  -connect mall.example.com:443 2>/dev/null \
  | openssl x509 -noout -dates
~~~

证书剩余天数少于 30 天时先手动 **sudo certbot renew** 并看日志；不要等
过期。Cloudflare 开代理时 HTTP-01 可能被挡，改用 DNS-01 插件，或续期时
临时灰云。

## 11. Nginx 配置说明（deploy/nginx-小满商城.conf）

### 11.1 结构

- **80 server**：只做 ACME 验证和 301 到 HTTPS。
- **443 server**：TLS、安全响应头、反向代理、gzip、1 MB 请求体上限。
- **upstream xiaoman_mall**：127.0.0.1:3000，keepalive 32。
- **location = /api/agent/chat**：SSE 专用，关闭缓冲、300 秒读超时。
- **location /api/**：普通 API 反代，60 秒超时。
- **location ~* ^/(assets|css|js)/**：静态资源反代 + 1 小时缓存。
- **location /**：页面和其余静态文件交给 Node。
- 可选注释块：让 Nginx 直接读 **public/assets**，绕过 Node。

### 11.2 SSE 为什么单独写

AI 助手 **POST /api/agent/chat** 返回 **text/event-stream**。只要中间任何
一层开启缓冲/压缩，浏览器就会“等一大段才一次出来”，看起来像不流式。
配置里做了这些：

- **location = /api/agent/chat** 精确匹配，避免被 **/api/** 规则吃掉。
- **proxy_buffering off;**
- **proxy_request_buffering off;**
- **proxy_cache off;**
- **gzip off;**
- **proxy_read_timeout 300s; proxy_send_timeout 300s;**
- **proxy_hide_header X-Accel-Buffering;** 再 **add_header X-Accel-Buffering no always;**
- **proxy_http_version 1.1;** 和 **Connection ""** 保持长连接。

后端本身也会发 **Cache-Control: no-cache, no-transform** 和
**X-Accel-Buffering: no**；两层都设置是兜底，不冲突。

### 11.3 安全响应头与重复问题

应用层（**server/index-服务入口.js**）已经发：

- **X-Content-Type-Options: nosniff**
- **X-Frame-Options: DENY**
- **Referrer-Policy: strict-origin-when-cross-origin**
- **Permissions-Policy: geolocation=(), microphone=(), camera=()**
- **Cross-Origin-Opener-Policy: same-origin**
- **X-Request-Id**

Nginx 层再补：

- **Strict-Transport-Security**（HSTS，仅 HTTPS）
- **Content-Security-Policy**
- **X-Permitted-Cross-Domain-Policies**
- 以及同一组基础头，统一由 Nginx 发。

为了避免同一个头出现两份，配置里对后端的
**X-Content-Type-Options / X-Frame-Options / Referrer-Policy /
Permissions-Policy** 用了 **proxy_hide_header**。所以：

- 验收时 **X-Frame-Options** 只应出现一次。
- 不要在别的 location 再写一遍 **add_header X-Frame-Options**；
  如果非要写，先确认不会和 server 级/后端重复。
- **CSP** 里 **style-src** 带了 **'unsafe-inline'**，因为前端 JS 生成的
  HTML 里有少量 **style="..."**；等这些改成 class 后再收紧。
- **HSTS** 配置默认是开启的。第一次上线如果还没确认证书续期，先注释掉
  HSTS 那行，确认 HTTPS 稳定后再打开；不要给一个还会回退 HTTP 的站点
  发长 max-age。
- 没加 **includeSubDomains**；等所有子域都上了 HTTPS 再加。

### 11.4 静态资源缓存

当前 **public** 由 Node 提供：

- HTML：**Cache-Control: no-cache**。
- 其它静态文件：**public, max-age=300**（本地实测）。
- Nginx 对 **/assets/、/css/、/js/** 覆盖成 **expires 1h**，并隐藏上游
  **Cache-Control/Expires**，避免重复。

文件名没有内容 hash，所以不要直接上 30 天；要长缓存先做文件名版本化。
图片多时可以让 Nginx 直接读 **public/assets**（配置里有注释块），但要先
解决权限：Nginx worker 通常是 **www-data**，代码目录是 **750**，读不到
**root:xiaoman** 的文件。可以给 assets 加 **o+rX**，或把 www-data 加进
xiaoman 组；不要为了省事把整个代码目录改成 777。

### 11.5 请求体上限

- Nginx：**client_max_body_size 1m**。
- 后端 router：请求体上限 **1024 * 1024**，超过返回 **413 / code 41301**。

超过 1 MB 时，Nginx 会先返回自己的 413（HTML），请求不会到后端；这是
预期行为。前端上传图片/大 JSON 前要先确认这个上限。

### 11.6 检查配置

~~~bash
sudo nginx -t
sudo nginx -T | less
sudo systemctl reload nginx
~~~

**nginx -T** 输出合并后的完整配置，适合确认 **add_header**、**location**
和 **proxy_hide_header** 的实际继承关系。

## 13. 公网验收清单

以下命令把 **mall.example.com** 换成真实域名。

### 13.1 HTTP 跳转

~~~bash
curl -sS -o /dev/null -w '%{http_code} %{redirect_url}\n' \
  http://mall.example.com/
~~~

期望 **301 https://mall.example.com/**。用 **-I** 看 Location 也可以。

### 13.2 首页与安全头

~~~bash
curl -sSI https://mall.example.com/ | sed -n '1,25p'
~~~

期望：

- **HTTP/2 200**（或 HTTP/1.1 200）
- **strict-transport-security: max-age=31536000**
- **content-security-policy: ...**
- **x-content-type-options: nosniff**
- **x-frame-options: DENY**（只出现一次）
- **referrer-policy: strict-origin-when-cross-origin**
- **permissions-policy: geolocation=(), microphone=(), camera=()**
- **x-request-id: ...**
- **cache-control: no-cache**

检查同名头数量：

~~~bash
curl -sSI https://mall.example.com/ \
  | grep -ci '^x-frame-options:'
# 期望 1，不是 2
~~~

### 13.3 健康检查

~~~bash
curl -fsS https://mall.example.com/api/health
~~~

期望 JSON：

~~~json
{
  "code": 0,
  "message": "ok",
  "data": {
    "status": "ok",
    "version": "1.0.0",
    "uptimeSeconds": 12,
    "mode": "local",
    "now": "2026-10-21T09:00:00.000Z"
  }
}
~~~

**/api/health** 不读数据文件，所以它返回 ok 不代表商品 JSON 一定正常；
还要测商品接口。

### 13.4 商品与分类

~~~bash
curl -fsS 'https://mall.example.com/api/products?pageSize=60' \
  | node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>{const j=JSON.parse(s);console.log('code='+j.code,'total='+j.data.total,'list='+j.data.list.length)})"

curl -fsS 'https://mall.example.com/api/categories' \
  | node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>{const j=JSON.parse(s);console.log('code='+j.code,'categories='+j.data.length)})"
~~~

本地实测基线：**total=26、list=26、categories=6**。服务器上如果商品被
运营改过，数字可以不同，但 **code=0** 且 list 不为空。

### 13.5 静态资源缓存

~~~bash
curl -sSI 'https://mall.example.com/assets/products/p01-听风AirOne真无线运动耳机.svg' \
  | grep -iE 'HTTP/|cache-control|expires|content-type'
~~~

期望 **200**、**content-type: image/svg+xml**、**cache-control: max-age=3600**
（Nginx 的 1 小时覆盖；Node 原始是 300 秒）。如果还是 300，说明请求没命中
Nginx 的静态 location，或配置没 reload。

### 13.6 AI 助手 SSE

~~~bash
curl -N -sS \
  -H 'Content-Type: application/json' \
  -d '{"message":"推荐一款适合通勤的双肩包"}' \
  -w '\n--- first_byte=%{time_starttransfer}s total=%{time_total}s\n' \
  https://mall.example.com/api/agent/chat
~~~

期望看到分事件输出：

~~~text
event: meta
data: {...}

event: delta
data: {...}

event: done
data: {...}
~~~

本地实测基线（开发机、本地规则引擎）：**4 个事件**（meta、2 个 delta、done），
首字节 **12 ms**，总耗时 **47 ms**，响应约 **764 bytes**。服务器上数字会
不同；关键看事件是不是**逐条出现**，而不是最后一次性刷出来。

检查 SSE 响应头：

~~~bash
curl -sS -D /tmp/sse-headers.txt -o /dev/null -N --max-time 5 \
  -H 'Content-Type: application/json' \
  -d '{"message":"你好"}' \
  https://mall.example.com/api/agent/chat
grep -iE 'content-type|cache-control|x-accel-buffering|content-encoding' \
  /tmp/sse-headers.txt
~~~

期望：

- **content-type: text/event-stream; charset=utf-8**
- **cache-control: no-cache, no-transform**
- **x-accel-buffering: no**
- 没有 **content-encoding: gzip**（SSE 不压缩）

### 13.7 Cookie 登录

先注册一个测试用户（用户名/密码换成你自己的，不要用弱密码）：

~~~bash
curl -i -c /tmp/xm-cookies.txt \
  -H 'Content-Type: application/json' \
  -d '{"username":"demo_user_01","password":"ChangeThis-Strong-Pass-123"}' \
  https://mall.example.com/api/auth/register
~~~

期望 **201**，并且 **Set-Cookie** 里包含：

~~~text
xm_session=...; HttpOnly; SameSite=Lax; Path=/; Max-Age=...; Secure
~~~

关键点：

- 走 HTTPS 时必须有 **Secure**；没有就说明 Nginx 没传
  **X-Forwarded-Proto https**，后端 **isSecureRequest** 判断失败。
- **HttpOnly** 是正常的，前端 JS 读不到 Cookie 不代表登录失败。
- **SameSite=Lax** 下，跨站 POST 不会带 Cookie；前后端要同源。

带 Cookie 访问当前用户：

~~~bash
curl -fsS -b /tmp/xm-cookies.txt https://mall.example.com/api/auth/me
~~~

期望返回当前用户；如果返回 **user: null**，看第 18.4 节。

### 13.8 404 页面

~~~bash
curl -sS -o /dev/null -w '%{http_code}\n' \
  https://mall.example.com/这个页面不存在
~~~

期望 **404**（不是 200，也不是 502）。页面内容应是
**public/404-页面不存在.html**。

## 14. 日志、监控与磁盘

### 14.1 应用日志（journald）

~~~bash
journalctl -u xiaoman-mall -f
journalctl -u xiaoman-mall -n 200 --no-pager
journalctl -u xiaoman-mall --since '1 hour ago' --no-pager
journalctl -u xiaoman-mall -p err --no-pager
journalctl -u xiaoman-mall -o cat -n 50
~~~

每条请求日志形如：

~~~text
3ebeca77 GET /api/health 200 3ms
ad2b6da9 POST /api/agent/chat 200 45ms
~~~

第一段是 **X-Request-Id**，和浏览器 Network 响应头对得上；最后是耗时。
排查慢请求先看这里。

journald 默认会按磁盘/时间轮转；不要再用 **logrotate** 管 journal。
需要限制 journal 大小时改 **/etc/systemd/journald.conf** 的
**SystemMaxUse=**，然后 **sudo systemctl restart systemd-journald**。

### 14.2 Nginx 日志

- **/var/log/nginx/xiaoman-mall.access.log**：带 **rt**（总耗时）和
  **urt**（后端耗时）。
- **/var/log/nginx/xiaoman-mall.error.log**：warn 及以上。

~~~bash
sudo tail -f /var/log/nginx/xiaoman-mall.access.log
sudo tail -f /var/log/nginx/xiaoman-mall.error.log
# 统计状态码
sudo awk '{print $9}' /var/log/nginx/xiaoman-mall.access.log | sort | uniq -c
# 找慢请求（rt 大于 1 秒）
sudo awk '$0 ~ /rt=[1-9][0-9]*\./ {print}' /var/log/nginx/xiaoman-mall.access.log | tail -20
~~~

Nginx 包自带 logrotate（**/etc/logrotate.d/nginx**），一般不用改。
**logrotate -d /etc/logrotate.d/nginx** 可以 dry-run 检查。

### 14.3 AI 轨迹

~~~bash
ls -lh /var/lib/xiaoman-mall/agent-traces.jsonl
sudo tail -n 3 /var/lib/xiaoman-mall/agent-traces.jsonl
~~~

轨迹里可能有用户消息，属于个人信息：

- 文件权限保持 **640**，目录 **750**。
- 不要随便下载/外发；排障时只取必要片段。
- 用 logrotate 控制大小（示例）：

~~~text
/var/lib/xiaoman-mall/agent-traces.jsonl {
    weekly
    rotate 8
    compress
    delaycompress
    missingok
    notifempty
    copytruncate
    su xiaoman xiaoman
}
~~~

放到 **/etc/logrotate.d/xiaoman-mall-traces**，先
**sudo logrotate -d /etc/logrotate.d/xiaoman-mall-traces** 检查。

### 14.4 监控

- 外部 uptime 监控探 **https://mall.example.com/api/health**，超时 5 秒，
  连续 3 次失败告警。
- **/api/health** 只说明进程活着；再探一个只读接口（如
  **/api/products?pageSize=1**）确认数据目录可用。
- 不要用“健康检查失败就自动 restart”当唯一手段：先告警，确认是进程挂
  还是数据/磁盘问题；盲目重启会掩盖根因。
- 磁盘：**df -h /var/lib/xiaoman-mall**；JSON 文件和 trace 会增长。
- 内存：**free -h**；1 GB 机器建议有 swap。
- 证书：**certbot certificates** 或外部 TLS 到期监控。

## 15. 备份 JSON 数据

### 15.1 备份什么

| 内容 | 路径 | 说明 |
| --- | --- | --- |
| 业务 JSON | /var/lib/xiaoman-mall/*.json | 商品、分类、购物车、订单、用户、会话 |
| AI 轨迹 | /var/lib/xiaoman-mall/agent-traces.jsonl | 可选，含用户消息 |

### 15.2 停机备份（推荐）

JSON 写入不是跨文件事务；最稳的是短暂停服再打包：

~~~bash
sudo install -d -m 750 -o root -g root /var/backups/xiaoman-mall
sudo systemctl stop xiaoman-mall
sudo tar -czf /var/backups/xiaoman-mall/data-$(date +%F-%H%M%S).tar.gz \
  -C /var/lib/xiaoman-mall .
sudo systemctl start xiaoman-mall
curl -fsS http://127.0.0.1:3000/api/health
~~~

验证压缩包：

~~~bash
ls -lh /var/backups/xiaoman-mall/
sudo tar -tzf /var/backups/xiaoman-mall/data-*.tar.gz | head
~~~

只想备份 JSON、不带 trace：

~~~bash
sudo tar -czf /var/backups/xiaoman-mall/json-$(date +%F-%H%M%S).tar.gz \
  --exclude='agent-traces.jsonl' \
  -C /var/lib/xiaoman-mall .
~~~

### 15.3 恢复

~~~bash
sudo systemctl stop xiaoman-mall
# 先把当前数据再备份一份，防止恢复错版本
sudo tar -czf /var/backups/xiaoman-mall/before-restore-$(date +%F-%H%M%S).tar.gz \
  -C /var/lib/xiaoman-mall .
# 恢复
sudo tar -xzf /var/backups/xiaoman-mall/data-2026-10-21-030000.tar.gz \
  -C /var/lib/xiaoman-mall
sudo chown -R xiaoman:xiaoman /var/lib/xiaoman-mall
sudo find /var/lib/xiaoman-mall -type d -exec chmod 750 {} +
sudo find /var/lib/xiaoman-mall -type f -exec chmod 640 {} +
sudo systemctl start xiaoman-mall
curl -fsS http://127.0.0.1:3000/api/health
~~~

恢复后检查商品数、订单数、登录是否正常；如果数据版本和代码不兼容，
回滚代码到对应版本（第 16 节）。

### 15.4 定时与异地

- 每天低峰（如 03:30）跑一次停机备份；用 cron/systemd timer。
- 保留 14–30 天；重要促销前手动加一份。
- 备份复制到另一台机器/对象存储，不要只留在同一块盘。
- 含用户/订单/密钥的备份要加密（age、gpg 或云厂商加密桶），
  并把加密密钥与备份分开存放。
- 定期做**恢复演练**；没验证过的备份不算备份。

### 16.1 代码回滚

按 15.3 恢复。注意：

## 17. 可选：Docker / Docker Compose

已经用 systemd 直装时，不要同时起容器，否则 3000 端口冲突。Docker 方案
适合“不想在宿主机装 Node”或“想用镜像固化版本”的场景。

### 17.1 前置

~~~bash
docker --version
docker compose version
sudo systemctl enable --now docker
~~~

当前用户不在 docker 组时，命令前加 **sudo**，或把用户加入 docker 组
（加入 docker 组等同于 root 权限，谨慎）。

### 17.2 构建与启动

在仓库根目录：

~~~bash
docker compose -f deploy/docker-compose.yml build
AGENT_MODE=local docker compose -f deploy/docker-compose.yml up -d
docker compose -f deploy/docker-compose.yml ps
curl -fsS http://127.0.0.1:3000/api/health
~~~

镜像基于 **node:22-alpine**，非 root 用户 **xiaoman（uid 10001）**，
**/app/data** 是命名卷 **xiaoman-mall-data**。容器根文件系统只读，
**/tmp** 是 tmpfs，所有 capability 被 drop。

### 17.3 环境变量与密钥

Compose 文件里的 **AGENT_ 系列**用宿主机环境变量插值：

~~~bash
# 推荐：用已有的 600 文件作为插值来源，不把密钥写进命令行历史
sudo docker compose --env-file /etc/xiaoman-mall.env \
  -f deploy/docker-compose.yml up -d
~~~

也可以：

~~~bash
export AGENT_MODE=llm
export AGENT_API_KEY='你的密钥'
docker compose -f deploy/docker-compose.yml up -d
unset AGENT_API_KEY
~~~

不要在 **deploy/** 下建会被提交的 **.env**。**docker compose config**
会打印插值后的配置（可能含密钥），排查时注意别贴出去。

### 17.4 数据卷与备份

首次启动时，空命名卷会从镜像的 **/app/data** 复制商品/分类种子；卷里
已有数据时不会被覆盖。升级镜像不会自动更新商品 JSON，需要单独导入。

备份：

~~~bash
docker compose -f deploy/docker-compose.yml stop
docker run --rm \
  -v xiaoman-mall-data:/data:ro \
  -v "$PWD":/backup \
  node:22-alpine \
  tar -czf /backup/xiaoman-data-$(date +%F-%H%M%S).tar.gz -C /data .
docker compose -f deploy/docker-compose.yml start
~~~

恢复时把 tar 解回卷，注意 uid 10001 的属主；必要时用临时容器
**chown -R 10001:10001 /data**。

### 17.5 日志、更新、回滚

~~~bash
docker compose -f deploy/docker-compose.yml logs -f --tail=100
docker stats xiaoman-mall
docker inspect --format '{{.State.Health.Status}}' xiaoman-mall
~~~

更新：改代码后重新 **build**，再 **up -d**；回滚把 **image** 改成旧 tag
再 **up -d**。容器日志已配 **json-file max-size=10m / max-file=3**。

### 17.6 Docker 下的 Nginx

Nginx 仍在宿主机上，反代到 **127.0.0.1:3000**；**deploy/nginx-小满商城.conf**
不用改。容器内 **HOST=0.0.0.0**，但端口只映射到宿主机回环地址，公网进不来。

## 18. 常见错误

### 18.1 502 Bad Gateway

现象：Nginx 返回 502，页面打不开；**error.log** 里常见
**connect() failed (111: Connection refused)**。

排查：

~~~bash
systemctl status xiaoman-mall --no-pager
journalctl -u xiaoman-mall -n 50 --no-pager
ss -lntp | grep 3000
curl -v http://127.0.0.1:3000/api/health
sudo tail -n 50 /var/log/nginx/xiaoman-mall.error.log
~~~

常见原因：

- Node 没启动/刚崩：看 systemd 日志里的报错。
- 端口不一致：env 里 **PORT** 改了，Nginx upstream 还是 3000。
- 监听地址不对：Node 绑了 **127.0.0.1**，Nginx 却去连别的地址/容器名。
- 数据目录权限：Node 启动时读商品 JSON 失败，进程退出。
- 容器方案：容器没起、端口没映射、Nginx 在另一个网络命名空间里连
  **127.0.0.1** 连不到容器（这种要把 Nginx 也放容器网络，或改 upstream）。

### 18.2 504 Gateway Timeout

现象：Nginx 等后端超时；**access.log** 的 **urt** 接近超时值。

排查：

- **/api/** 默认 **proxy_read_timeout 60s**；AI 对话的
  **/api/agent/chat** 是 **300s**。
- 大模型 **AGENT_TIMEOUT_MS=30000**，通常不会到 60s；如果上游 API 很慢，
  先看 trace 和 Node 日志。
- 数据库/文件锁：本项目是 JSON 同步写，正常不会锁很久；检查磁盘满/
  IO 卡住。
- 不要在 **/api/** 全局把超时调到 300s 掩盖问题；先定位是哪个接口慢。

~~~bash
sudo awk '{print $NF, $0}' /var/log/nginx/xiaoman-mall.access.log | tail -20
journalctl -u xiaoman-mall --since '10 min ago' --no-pager | tail -50
df -h
~~~

### 18.3 SSE 不流式（最后一次性出来）

按顺序查：

1. Nginx 是否命中了 **location = /api/agent/chat**：
   **sudo nginx -T | grep -n 'agent/chat'**。
2. 该 location 是否有 **proxy_buffering off**、**gzip off**、
   **proxy_read_timeout 300s**。
3. 响应头是否有 **x-accel-buffering: no**、
   **content-type: text/event-stream**、没有 **content-encoding: gzip**。
4. CDN/云 WAF 是否缓冲：Cloudflare 要关掉对 SSE 的缓冲/压缩，或让
   **/api/agent/chat** bypass；有些 CDN 直接不支持流式。
5. 浏览器是否用 **fetch** 正常读流；DevTools Network 里看 EventStream，
   不要只看最终 response。
6. 用 **curl -N** 绕过浏览器和前端代码：

~~~bash
curl -N -sS -H 'Content-Type: application/json' \
  -d '{"message":"你好"}' \
  https://mall.example.com/api/agent/chat
~~~

如果 curl 是逐条、浏览器不是，问题在前端/CDN；如果 curl 也一次性，
问题在 Nginx/后端。后端本身已经写了 **: connected** 和 15 秒心跳，
长时间无输出时会看到注释行。

### 18.4 Cookie 不生效 / 登录状态丢失

现象：登录接口 200，但刷新后 **/api/auth/me** 返回 **user: null**；
或者浏览器根本不发 **xm_session**。

排查：

~~~bash
# 看响应头有没有 Set-Cookie，Secure/HttpOnly/SameSite 是否正确
curl -i -c /tmp/xm-cookies.txt -H 'Content-Type: application/json' \
  -d '{"username":"demo_user_01","password":"你的密码"}' \
  https://mall.example.com/api/auth/login

# 看后续请求有没有带 Cookie
curl -v -b /tmp/xm-cookies.txt https://mall.example.com/api/auth/me
~~~

常见原因：

- **Nginx 没传 X-Forwarded-Proto**：后端认为不是 HTTPS，Cookie 不加
  **Secure**；如果你在 HTTPS 页面上要求 Secure，就会对不上。配置里已经
  有 **proxy_set_header X-Forwarded-Proto $scheme**，检查是否被别的
  location 覆盖。
- **TLS 在 CDN/负载均衡终止**：Nginx 看到的是 http，**$scheme** 是 http；
  要在可信代理层传 **X-Forwarded-Proto: https**，并只信任自己的代理，
  不要盲目信任客户端伪造的头。
- **域名不一致**：在 **www** 登录、跳 **mall** 使用，Cookie 的 Host 不同；
  统一 301 到一个域名，或设置正确的 Cookie Domain（本项目默认 Host-only）。
- **SameSite=Lax**：跨站 POST 不带 Cookie；前后端要同源，或按需调整
  SameSite（改代码，不在部署层硬改）。
- **HttpOnly**：前端 JS 读不到是正常的，不要用 **document.cookie** 判断
  登录；用 **/api/auth/me**。
- **Secure + HTTP 调试**：在 http:// 下测，浏览器不会发 Secure Cookie；
  用 https 或 SSH 隧道到本机 http 时注意这个差异。
- **Cookie 被清**：退出接口会清 Cookie；多标签页/多账号测试时先清站点数据。

### 18.5 413 Request Entity Too Large

- Nginx **client_max_body_size 1m**；后端 router 也是 1 MB。
- 上传大图/大 JSON 会先被 Nginx 挡，返回 HTML 413；这是预期。
- 真要放大，先评估内存和滥用风险，Nginx 与后端两处一起改，并加限流。

### 18.6 静态资源 404 / 403

- 404：路径大小写、文件名（中文）、**public** 目录是否随代码部署。
- 403：Nginx 直连 **public/assets** 时 worker 没读权限；看
  **error.log** 的 **Permission denied**。
- 改了 Nginx 静态 location 后没 reload；**nginx -t** 后 reload。
- 浏览器缓存了旧 404；用 **curl -I** 加随机查询参数确认。

### 18.7 500 / 商品为空

~~~bash
journalctl -u xiaoman-mall -n 100 --no-pager
ls -l /var/lib/xiaoman-mall/
curl -fsS http://127.0.0.1:3000/api/products?pageSize=1
~~~

- 商品/分类 JSON 没复制到 **XM_DATA_DIR**。
- JSON 格式坏了（手工编辑少逗号/括号）：用
  **node -e "JSON.parse(require('fs').readFileSync('...','utf8'))"** 验证。
- 文件属主不是 xiaoman，Node 读不了。
- 修改了 **XM_DATA_DIR** 但没重启。

### 18.8 服务启动失败 / 反复重启

~~~bash
systemctl status xiaoman-mall --no-pager -l
journalctl -u xiaoman-mall -n 100 --no-pager
sudo -u xiaoman /usr/bin/node -v
sudo -u xiaoman test -r /opt/xiaoman-mall/xiaoman-mall/server/index-服务入口.js && echo readable
sudo -u xiaoman test -w /var/lib/xiaoman-mall && echo writable
~~~

- **EnvironmentFile** 缺失/格式错：systemd 启动前就失败。
- **ExecStart** 路径错：**command -v node** 确认。
- **WorkingDirectory** 错：代码不在约定路径。
- **ProtectSystem=strict** 下应用试图写代码目录：数据必须写
  **XM_DATA_DIR**，trace 写 **XM_TRACE_FILE**。
- 端口被占用：见 18.9。

### 18.9 EADDRINUSE

~~~bash
sudo ss -lntp | grep ':3000'
sudo lsof -i :3000
~~~

找到占用进程：是旧的 node、还是 Docker 容器。不要直接 **kill -9**；
先 **systemctl stop xiaoman-mall** 或 **docker compose stop**，确认没有
在途写入，再处理。改端口时同步改 **/etc/xiaoman-mall.env** 和 Nginx
upstream。

### 18.10 证书申请/续期失败

- DNS 没生效：**dig +short** 确认。
- 80 被安全组/ufw/CDN 挡：**curl -i http://域名/.well-known/acme-challenge/ping**。
- webroot 不一致：Nginx **root** 必须指向 **/var/www/certbot**。
- 请求过多：用 **--staging** 调试，别反复打生产。
- 续期 hook 没执行：**systemctl reload nginx** 手动测；看
  **/var/log/letsencrypt/letsencrypt.log**。
- Cloudflare 代理：先灰云，或改用 DNS-01。

### 18.11 AI 助手报错 / 不回复

- **AGENT_MODE=local**：不需要 Key；如果仍报错，看 Node 日志和 trace。
- **AGENT_MODE=llm**：Key 无效、余额不足、网络不通、模型名错。
- 服务器出网被限制：**curl -I https://api.deepseek.com** 测；必要时开
  出站 443。
- 上游超时：**AGENT_TIMEOUT_MS** 默认 30 秒；看 trace 里的错误。
- 先用 **local** 排除部署问题，再切 **llm** 排除供应商问题。

### 20.3 应用层已实现、Nginx 层补充的边界

- **GET /api/health**：server/index-服务入口.js 直接处理，不经过业务
  路由、不读数据文件；返回 **Cache-Control: no-store**。Docker healthcheck
  和外部监控都用它。
- **基础安全响应头**：server/index-服务入口.js 已设置 nosniff、
  X-Frame-Options、Referrer-Policy、Permissions-Policy、COOP 和
  X-Request-Id。
- **HSTS、CSP、X-Permitted-Cross-Domain-Policies**：应用层没有，由 Nginx
  站点配置补；不要误以为后端已经发。
- **X-Frame-Options 重复**：后端发 DENY，Nginx 也发；配置里已用
  **proxy_hide_header** 去掉上游同名头，验收时用
  **grep -ci '^x-frame-options:'** 确认只有 1 份。
- **CSP 的 style-src 'unsafe-inline'**：前端 JS 生成的 HTML 有内联 style；
  这是当前兼容做法，后续把内联样式改成 class 后可收紧。
- **静态缓存**：Node 给 **max-age=300**；Nginx 对 assets/css/js 覆盖成
  **1h**。要更长缓存先做文件名 hash/版本化。
