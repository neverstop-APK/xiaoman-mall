# 演示脚本 · 8 分钟讲完这个项目

> 这份脚本按「先跑通、再讲清、最后答疑」组织。每一段都给了操作、要说的点，以及面试官可能追问的问题。

## 一、开场（30 秒）

可以照着说：

> 这是一个叫「小满商城」的购物网站，前端是原生 HTML/CSS/JS，后端是 Node 原生 http 模块，没有用框架，也没有第三方依赖。
> 首页负责推荐和热卖，搜索、分类和价格筛选集中在「全部商品」页；再往下是商品详情、侧拉购物车、下单和模拟支付、订单结果查询，桌面到手机都做了响应式。
> 商品数据放在服务端的 JSON 文件里，前端所有数据都通过接口拿。

## 二、主流程演示（3 分钟）

按这个顺序点，不要跳：

1. **首页**：指出导航图标 hover 会上浮变色、搜索框、购物车角标；往下滚，指出 6 个分类入口、本周热卖 8 件、编辑推荐和两个专题位。说明首页故意不放筛选，避免首屏被工具条占满。
2. **进目录**：点「全部商品」或任一分类卡，进入完整目录。在搜索框输入「耳机」回车，说「结果变成 5 件，地址栏多了 `?keyword=耳机`，刷新后结果还在」。
3. **筛选叠加**：点「数码」，再点价格「100–299」，说「关键词、分类、价格三个条件在服务端一起算，不是前端把数据全拿回来再过滤」；再切「价格从低到高」，指出顺序变化。
4. **详情**：点一件商品，指出价格、原价与折扣、库存状态、规格表、卖点列表、相关推荐；把数量改成 2，加购。
5. **购物车**：右侧抽屉滑出，指出单项小计、总金额、步进器、删除、清空；点「去结算」。
6. **下单**：填收货人、手机号、地址，故意先填错手机号，展示前端校验；改对后提交，指出「支付中」的 900ms。
7. **结果页**：指出订单号、支付成功状态、商品明细、金额、收货信息、下单时间；刷新页面，订单还在（因为地址栏带订单号）。
8. **订单列表**：回到「我的订单」，指出历史订单；演示取消未支付订单（可以另开一单不支付）。
9. **响应式**：拖窄窗口到手机宽度，或 DevTools 切 390px，指出导航只剩图标、商品改单列、抽屉占满宽度；再用 250% 缩放说明没有横向滚动。

## 三、讲清三条链路（3 分钟）

### 1. 一次搜索发生了什么

- 前端：`products-全部商品页逻辑.js` 把筛选条件存进 `state`，同步到 URL，然后调用 `api.products.list()`；
- 请求：`GET /api/products?keyword=耳机&category=数码&maxPrice=99&page=1&pageSize=8`；
- 后端：`router` 解析 query → `catalog` 服务按关键词、分类、价格依次过滤 → 排序 → 分页；
- 响应：`{ code: 0, data: { list, total, totalPages } }`；
- 前端：清空列表 → 渲染骨架屏 → 拿到数据后替换成卡片 → 更新分页器和「共 N 件」。

可以补一句：每个请求带自增序号，快速连点时只渲染最后一次结果，避免旧数据覆盖新数据。

### 2. 购物车为什么放服务端

- 加购请求只带 `productId` 和数量，价格、库存、小计都由服务端算；
- 下单时再校验一次库存和价格，防止前端改价；
- 服务端返回整辆车的快照，前端 `cartStore` 订阅后，顶栏角标、抽屉、结算弹窗一起更新；
- `cartId` 存在 localStorage，换页面也能找回同一辆车。

### 3. 下单与支付

- 前端只做格式校验，金额不参与计算；
- 后端读购物车 → 校验商品和库存 → 用数据库单价重算 → 生成 `XM+日期+6位十六进制` 订单号 → 扣库存、加销量、清空购物车、落盘；
- 支付是第二次请求，把状态从 `pending` 改成 `paid`，重复支付会返回 409；
- 结果页用订单号查询，所以刷新、复制链接都能打开。

## 四、高频追问与回答（2 分钟）

**问：为什么不用 Vue / React？**

> 考核允许原生，我想把基础打牢：DOM 操作、事件委托、模块化、状态订阅都是手写的。数据量只有 26 件、页面只有 4 个，原生足够，而且没有构建步骤，打开就能跑。

**问：后端做了什么？**

> 三件事：提供数据（商品、分类、推荐）、维护状态（购物车、订单、库存）、做校验和计算（参数、库存、金额、订单号）。前端不信任自己的计算结果。

**问：接口报错怎么排查？**

> 先看 Network 的 Status 和 Response 里的 code，对照错误码表；4xx 多半是参数问题，看 Payload；404 且返回 HTML 说明路径没进接口；Failed to fetch 说明服务没起或端口不对；最后看服务端日志的时间戳。

**问：状态管理怎么做的？**

> 一个很小的发布订阅：`cartStore` 保存购物车快照，`subscribe()` 注册回调，任何修改都先请求接口，再用返回的快照 `emit`，所有订阅者（角标、抽屉、结算弹窗）自动重渲染。没有引入任何库。

**问：响应式怎么保证 50%–250% 不错乱？**

> 网格用 `minmax(min(100%, 240px), 1fr)` 自动降列；字号和间距用 clamp/rem；关键断点 960/860/640/400；窄屏隐藏导航文字但保留图标；抽屉和弹窗用 `max-width: 100%`，不会溢出。250% 缩放下实测无横向滚动。

**问：遇到最难的问题？**

> 可以讲一个真实的：窄屏下导航原本整块 `display: none`，导致手机上完全没有导航；后来改成只隐藏文字、保留图标。还有购物车行的布局，一开始删除按钮被 flex 拉伸到中间，后来把一行拆成「名称 / 单价+删除 / 步进器+小计」三段才对。

**问：如果商品变成 1 万件怎么办？**

> 现在分页和筛选都在服务端，接口不用改；瓶颈会在 JSON 全量读进内存和同步写文件，下一步换 SQLite 或 MySQL，把筛选条件下推到 SQL，加索引；前端可以加虚拟列表。

## 六、可以主动提的不足

- 没有登录，订单只存在当前浏览器；
- 历史订单是本地存单号再逐个查，没有「按用户查列表」的接口；
- 支付是模拟的，没有对接真实支付；
- 数据量小，JSON 够用，但并发写入需要换数据库。
